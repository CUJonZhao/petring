# DeskPet 项目 Proposal

**版本：** 0.1，2026-11-07

**定位：** 以 Delta 为第一只验证犬的远程陪伴桌宠；先做软件，再验证硬件与联网。

## 1. 产品目标

当主人不在家、在电脑前工作时，桌面上的 Delta 角色根据家中狗狗的近期行为切换动作，让主人看到“现在大概在做什么”。产品应明确区分**观测到的行为、推测的行为和信号中断**，不展示情绪判断、健康诊断或伪装成实时的旧状态。

首要场景是 Delta 在有家用网络的环境里活动，主人在外使用 macOS 桌宠。用户可上传多角度照片制作个性化角色；长期目标是可辨认、质感较真实的 3D，而不只是通用犬模型。

## 2. 范围与交付

| 阶段 | 主要交付 | 验收门槛 |
|---|---|---|
| A. 软件体验 | macOS 桌宠、照片管理、角色资源、待机／趴卧／走动／喝水／叫声动画、模拟事件输入 | 不接硬件也能完整演示；动作起止和切换自然；断开输入后显示“无法判断”。当前已形成可运行原型，画质仍待精修。 |
| B. 视觉制作 | Delta 专用的高质量网格、UV/材质、长毛表现、骨骼与动画片段，支持换角色 | 从正面和侧面都能认出 Delta；四足落地、转身、趴卧和舔水无明显穿模；在目标 Mac 上流畅运行。 |
| C. 行为验证 | 已标注的 Delta 项圈数据、分类器与误报分析 | 每类行为都用未参与训练的日期和场景验证，报告 precision、recall、延迟及每天误报次数；达不到门槛时只显示更粗的状态。 |
| D. 远程链路 | 家中设备到事件服务、认证的加密连接、重连和新鲜度控制 | 家中网络在线时主人可远程看到近期事件；断线、断电或消息过期时明确显示不可判断。 |

阶段 A 与 B 可并行；C 的数据采集可以用现有硬件启动。远程链路先接模拟事件，再接真实分类结果，避免把模型、识别和联网问题混在一起调试。

## 3. 行为定义

| 桌宠行为 | 初期数据依据 | 表达方式 |
|---|---|---|
| 静止／趴卧 | IMU 低活动量与姿态变化 | “正在休息”或“可能在趴着”；仅靠项圈不能确认真正睡着。 |
| 走动 | IMU 周期运动与持续时间 | 识别后播放步态，不把一次抖动当成走路。 |
| 喝水 | 待验证的项圈运动模式；必要时结合水碗传感器 | 验证前保持“可能在喝水”，与舔舐、进食等相似动作区分。 |
| 叫声 | 先评估 IMU 能否区分颈部振动；不足时再评估本地音频特征 | 只发送“检测到叫声”事件；若用麦克风，优先设备端处理，不上传原始室内音频。 |
| 无法判断 | 低置信度、连接中断、设备不在佩戴状态或事件过期 | 停止模拟成直播中的动作，显示连接或数据状态。 |

研究说明这条路线**可行但不能直接套用论文准确率**：一项大规模单项圈加速度计研究报告了喝水行为检测的高敏感度；另一项 45 只犬的研究中，颈部传感器的七类活动分类最高约 75%，静态姿势尤其难分。这些差异说明传感器位置、佩戴方式、犬只和训练数据会左右结果，必须对 Delta 的实际佩戴数据单独验证。参见 [单项圈行为识别研究](https://pmc.ncbi.nlm.nih.gov/articles/PMC8228965/)与[项圈／胸背传感器对比研究](https://www.sciencedirect.com/science/article/pii/S0168159121001805)。另有[外部验证研究](https://pmc.ncbi.nlm.nih.gov/articles/PMC5706712/)支持步行、休息、进食和喝水的识别潜力，但其专用设备和实验条件不是本项目的已验证性能。

## 4. 技术架构

```text
Delta 身上的 IMU／可选传感器
        ↓  家中 Wi-Fi（初版）
设备端特征与行为事件 → 家中网络／鉴权事件服务 → 加密 WebSocket → macOS DeskPet
        ↓                                                  ↓
本地原始数据与标注，用于训练和复核                   动画、状态来源、最后更新时间
```

已有 ESP32 Feather/HUZZAH32 V2、LSM6DSOX、供电和记录固件可作为数据采集起点。现有固件主要做离家记录与回家上传；本项目需要新增**家中在线事件通道**。初版在 Delta 处于家中 Wi-Fi 覆盖时由设备直接发小型状态事件；若后续改用低功耗 BLE 项圈，家中需有持续在线的手机或网关转发。不要把 BLE 与公网连接混为一谈。

桌宠现有 JSON 原型为 `state`、`confidence`、`timestamp`。正式协议再加入 `device_id`、单调递增的 `sequence`、`observed_at`、`expires_at` 和 `source`，并明确时钟不同步、重发、乱序及撤销旧状态的规则。真实远程连接必须有设备配对、访问控制和 TLS；可观察事件优先于连续上传原始 IMU 或音频。

## 5. 模型与动作制作路线

当前 `Delta.blend` 是可编辑的风格化资产，可继续做交互验证。要达到更真实的 3D，应独立完成：

1. 收集近距离、同一天、平视、无遮挡的站立正面、左右侧面和背面照片，尽量同时拍自然光环绕视频；现有侧身照较远、部分照片有背带和牵引绳，无法可靠还原全身比例和花纹边界。
2. 根据参考图手工精修犬体比例、头脸与耳朵，完成拓扑、UV、毛色贴图和长毛表现。自动照片建模可以作为草稿来源，但产出必须逐面检查。
3. 制作含脊柱、头颈、下颚、四肢、尾巴的骨骼；分别制作走路循环、转圈卧下、呼吸闭眼、走到碗前舔水和叫声片段。每个动作设过渡时间、可中断点和落地约束。
4. 在真实桌面窗口尺寸下检视正面、侧面和半侧面，不只看 Blender 大图；记录穿模、脚滑、碗与嘴的接触偏差及运行负载。

高质量写实模型主要是美术与动画制作工作，单靠继续调整 SceneKit 球体或旋转参数无法达到目标。是否请 3D 角色美术协作，可在软件交互确定后决定。

## 6. 数据与验证计划

- 先用现有 IMU，不立即购买新的 ring。采集 Delta 的静止、走动、喝水、进食、舔舐、叫声及设备摘下等视频对照样本；同时保留无人为提示的日常背景片段，防止只在演示动作里表现良好。
- 按**日期与场景**划分训练集和测试集，避免同一次动作的相邻窗口同时进入训练和测试。分别报告每类 precision、recall、漏报、误报／天和事件开始延迟。
- 第一轮只把通过验证的类接到桌宠；喝水、叫声达不到可靠度时回退为“正在活动”或“无法判断”，不硬凑完整动画。
- 先验证佩戴舒适性、电池和室内 Wi-Fi 覆盖，再考虑低功耗 BLE、新外壳、麦克风或水碗传感器。购买决定以误报、续航和覆盖数据为依据。

## 7. 主要风险与边界

| 风险 | 处理原则 |
|---|---|
| “睡着”和“静止”混淆 | 产品只承诺可观测的休息／趴卧，不把 IMU 的低活动量当作睡眠事实。 |
| 喝水、舔舐、进食动作相似 | 保留置信度和“可能”措辞；必要时用水碗侧辅助信号，不单凭几次头部动作断言。 |
| 误报造成虚假的陪伴感 | 事件过期立即显示未知；记录最后更新时间和信号来源；为模型设置最低可靠度门槛。 |
| 隐私与安全 | 原始照片默认仅在本地；远程只传状态事件；若增加音频，优先本地提取特征并明示授权。 |
| 佩戴与续航 | 先复用并验证已有原型，确保固定不松动、无可咬裸线；长期佩戴和量产外壳在单独阶段评估。 |

## 8. 工期与资源初估

以下是供排期的**工作量估计，不是交付承诺**；3D 美术质量和 Delta 的行为样本量是最大的变量。假设有 1 名应用／后端开发、可参与的固件／算法开发，以及 1 名熟悉四足角色的 3D 美术（可兼职）；同一人承担多个角色时工期会拉长。

| 阶段 | 粗估工作量 | 最主要的不确定性 |
|---|---|---|
| A 软件体验从原型到稳定版 | 2–4 周 | 动作切换、窗口交互和异常状态的打磨。 |
| B 写实角色与动作 | 4–8 周或更久 | 毛发、可辨认度、四足骨骼与多动作制作。 |
| C 采集与验证 | 4–6 个日历周，可与 B 并行 | 日常场景标注量，尤其是喝水和叫声。 |
| D 远程链路与试用 | 2–4 周 | 家中网络覆盖、认证与断线恢复。 |

近期不因本 Proposal 采购新主控或传感器；先复用已有 ESP32 和 LSM6DSOX。若决定外包写实角色，先以明确的模型视角、动作清单和验收画面询价，再确定预算。

## 9. 近期最小交付顺序

1. 把现有桌宠动作从节点旋转升级成可复用的骨骼片段和过渡系统；完成 Delta 轮廓与材质的第二轮美术评审。
2. 固定事件协议、模拟网关和断线场景；让软件在没有项圈时也能持续调试。
3. 用现有硬件采集视频标注数据，先验证静止／走动，再挑战喝水与叫声。
4. 只把通过验证的行为接入家中在线链路；再做远程小范围试用。

**立项判断：** 软件与远程事件链路可以先做；个性化写实 3D 与细分行为识别都可实现为研发目标，但质量取决于素材、美术投入和 Delta 实测数据，不能把当前原型视为这两项已完成。
